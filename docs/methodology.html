The quality bar

Skillproof is a tool for upgrading your AI environment — and the reason you can trust what it hands you is this protocol. Every listing is checked against its real source before it appears, and labeled by exactly how far that check went. Three tiers, in descending strength:

TierLive countWhat was actually doneWhat it does not establish
tested & graded … Installed in a sandbox, probed, source read by a person, worksheet published —
reviewed … Full source read by an automated reviewer, pinned to one commit That it works. Nothing was installed or executed.
scouted … Repo verified real, scanned for known-malicious patterns What the code does. Nobody read it.

As of right now, no entry has reached the reviewed tier. The protocol below is published and enforced, but it has not been pointed at the catalogue yet — so every entry is still labelled scouted on the site, and nothing claims otherwise. This sentence disappears on its own once the first review lands.

If we didn't run it, we don't grade it. If we didn't read it, we don't say we reviewed it. There are no placeholder grades, and the counts on every page are computed from the catalog file rather than typed in.

Conflict of interest: we do not grade our own skills. Skillproof-family tools, if ever listed, are tagged house — not graded.

Tested & graded — five dimensions · 0–4 each · effectiveness ×2 · total /24

4. Maintenance (×1) — objective recency

Last meaningful commit: <3 months = 4 · <6 = 3 · <12 = 2 · older = 1 · dead = 0. Deductions (floor 0): −1 for issues ignored >60 days; −1 for hardcoded dead models/APIs.

5. Safety (×1) — every line gets read

Before anything executes, every line of the skill's source is read — SKILL.md, scripts, manifests, hooks. Start at 4, deduct: −1 undisclosed network calls · −1 ungated writes outside the project · −1 remote-exec patterns even if disclosed · −1 credential/env reads without need.

Auto-F override: undisclosed exfiltration, credential harvesting, destructive defaults, or deliberately obfuscated code = F overall regardless of other scores, delisted with the reason published.

The reviewed tier — read is not run

"Review the source before installing" is useless advice for the person who came here because they can't. So an automated reviewer (scripts/deep_review.py, Claude Opus 5) reads the source and answers the three questions that actually decide whether you install something. It publishes exactly four fields plus its own receipts:

  • What it does (review.does) — one plain sentence.
  • What it touches (review.touches) — from a fixed vocabulary of eight values (reads/writes project files · network calls · reads credentials/keys · runs shell commands · installs dependencies · writes outside the project · no side effects). The build rejects any value outside that list, so the labels mean the same thing on every entry and can be filtered on.
  • How to undo it (review.undo) — taken from what the source says. Where the source doesn't say, the field reads not documented by the author. That is a finding we publish, not a gap we fill with a guess.
  • What the review couldn't tell you (review.limits) — published verbatim, including on the entries where it is unflattering.
  • Scope (review.scope) — which files were read, how many bytes, and what was left out. Reviews are capped at 40KB per entry, so a 200-skill library is reviewed in part and says so; oversized documents are truncated and the cut is named.

What "reviewed" does not mean

Nothing was installed. Nothing was executed. Nobody watched it work. A reviewed entry carries no grade, no score, and no worksheet — the build fails if one ever tries to. A source read can be fooled by code that behaves differently at runtime, and it cannot tell you whether the thing is any good. Reading is not running; the tier exists to name that gap rather than paper over it.

Enforced, not promised: the honesty gate scans review prose for phrases that imply execution — "we tested", "we ran", "verified working" — and fails the build on a hit. The word choice is not left to whoever writes the prompt.

The pinning rule — why a review can't quietly go stale

Every review records review.source_sha: the exact commit whose bytes were read, taken from the clone the reviewer read (git rev-parse HEAD), not from a branch name. A branch moves; a commit doesn't.

  • Each refresh re-reads the repo's current HEAD into signals.head_sha.
  • When review.source_sha no longer matches it, the build automatically demotes the entry back to scouted, archives the old review under review_stale with the reason, and logs the demotion (validate_index.py --downgrade-stale).
  • If that step is ever skipped or broken, the honesty gate treats a stale review as a blocking error and the build stops. Belt and braces, deliberately: the fix keeps the catalog current without a human, and the gate means a decayed claim cannot ship even if the fix fails.

So a reviewed badge on this site means: the source at the commit that is live right now was read end to end. It expires by itself.

The scouted tier — found is not read

The scout (the workbench's fallback, the installable scout skill, and the MCP server's find_resources) surfaces resources we have not graded. Each scouted entry carries exactly four triage receipts, checked on the date shown:

  • Provenance — repo verified real via the GitHub API: author, stars, created-when.
  • License — the license field/file as found; "none detected" is reported plainly.
  • Freshness — last push date, with a flag when it's been quiet >6 months.
  • Safety skim — an automated scan of the repo's text for known-malicious patterns: remote-exec pipes, credential and SSH-key reads, decode-then-execute. It is a pattern match, not a reading. Anything it flags is pulled off the site entirely and parked in grading/quarantine.json — we don't list something we suspect and label it, because listing it is still advertising it. Only a person, having read the flagged lines, can restore one.

So scouted means nothing known-bad was found, not nothing bad is there. The full read is the reviewed tier above; until an entry reaches it, the catalog says so plainly rather than letting the absence of a warning read as a clearance.

Hard wall: neither scouted nor reviewed entries ever carry a grade, a score, or a worksheet, and scouted entries carry no install command. The honesty gate (scripts/validate_index.py) fails the build if one tries. A scan is a screen, a read is a description, and a grade is a test — the three are never merged.

Freshness & disputes

  • Grades older than 90 days are flagged stale — re-verify pending on the site.
  • Reviews don't expire on a clock, they expire on a commit: the moment upstream moves past the reviewed sha, the entry drops to scouted until it is re-read. A review is never "a few weeks old" — it either describes the live code or it is gone.
  • Re-grading a newer version supersedes the old worksheet — append-only, history never edited.
  • Authors who dispute a grade can open an issue; we re-run the protocol and publish the re-test either way.

Protocol notes (v1.0)

  • Probe model pinned to a mainstream daily-driver tier (Claude Sonnet class), fresh headless session per probe.
  • Test environment: disposable Linux container, clean fixture project per skill; mutating probes get isolated fixtures.
  • Safety read-through happens before anything executes; third-party skills run only inside the sandbox.
  • Every score carries a one-line "why" — in the worksheet and in the site data. A number without a reason doesn't ship.
  • Protocol mistakes (a contaminated fixture, a failed run) are re-run and recorded in the worksheet, not papered over.
